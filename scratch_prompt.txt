# 12. The split that prevents overfitting

This is probably the **single most important part**.

Do **not** do:

```python
train_test_split(df, test_size=0.2)
```

on all windows.

Suppose engine `E17` produces:

```text
100,000 windows
```

A random split could give:

```text
80,000 → train
20,000 → test
```

That's leakage.

The model sees almost the same operating trajectory during training and testing.

Instead split by **engine/run**:

```text
195 runs

TRAIN      70%
VALIDATION 15%
TEST       15%
```

Approximately:

```text
137 runs → train
29 runs  → validation
29 runs  → test
```

And make sure **no windows from the same run occur in different splits**.

Even better, hold out some operating regimes in the test set.

For example:

```text
TRAIN
0–15k ft
-5–40°C

TEST
15–20k ft
40–45°C
```

Then you're testing whether the system generalizes.

# 13. Class balance

Keep the fault classes approximately balanced initially.

Don't create:

```text
100,000 normal
10,000 injector
1,000 misfire
500 overheating
```

and then celebrate 95% accuracy.

The model could become a very successful "normal engine" detector.

Start roughly balanced.

Later, create a more realistic imbalanced test set and report:

* accuracy
* macro F1
* precision
* recall
* confusion matrix

**Macro F1 is particularly important** because it prevents a large normal class from hiding terrible performance on rare faults.

# 14. How many windows will this give you?

Suppose:

```text
195 runs
× 4 hours average
× 3600 sec/hour
```

At 1 Hz:

$$
2,808,000
$$

raw timesteps.

But using 30-second windows with overlap, you could generate hundreds of thousands of samples.

**Do not necessarily train on all of them.**

Highly overlapping windows:

```text
t = 0–30
t = 1–31
t = 2–32
t = 3–33
```

are almost identical.

That is another route to overfitting.

Use perhaps:

```text
30 s window
5 s stride
```

or even:

```text
30 s window
10 s stride
```

initially.

That gives you plenty of training examples without absurd redundancy.

# 15. XGBoost configuration

Don't start with a monster model.

Start around:

```text
n_estimators       = 300–600
max_depth          = 4–7
learning_rate      = 0.03–0.08
subsample          = 0.7–0.9
colsample_bytree   = 0.7–0.9
min_child_weight   = 3–10
reg_alpha          = small
reg_lambda         = 1–10
```

And use:

**early stopping on validation data.**

You want the model to stop once validation performance stops improving.

More trees are not automatically smarter. They are often just more confident about memorizing your simulator.
